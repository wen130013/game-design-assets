## ⚠️ 工作规范（血泪教训，务必遵守）

### 规范 1：改完必须构建，否则用户看的是旧版本

```
改代码 → LSP 诊断（0 error）→ 验证 → build 工具 → 告诉用户可以预览
```

**踩过的坑**：改完代码没构建就去汇报"已经修好了"，用户预览看到的还是旧画面，
以为没修好，白折腾好几轮。

### 规范 2：不许一次性大改，必须小步验证

**踩过的坑**：地图描边一次性全局改动 → 引入裂缝、双线、远处消失，
用户多次不满意，反复返工。

**正确做法**：
- 一次只改一个点 → 立刻 LSP + 构建验证 → 确认没问题再改下一个
- 涉及多文件的大改（如拆文件、改数据模型）→ **先 git commit 保底**，再动手

### 规范 3：改动范围严格匹配用户要求

用户说"优化这个面板" → 只改这个面板，**不要顺手改地图/其他系统**。
用户多次强调："不要为了局部问题重做整张地图"。

### 规范 4：不凭记忆答，先查代码/查证

**踩过的坑**：对 CK3 规则、地图性能、游戏数据结构做过未经核实的断言，被用户纠正。

**正确做法**：
- 涉及"代码里现在怎么写的" → 读代码
- 涉及"别的游戏怎么做的" → 用 `web_extractor` 查证，注明来源
- 不确定就直说"我不确定，我去查"

### 规范 5：报告结果要诚实

- 没做的就说没做，不要用"已经好点了"这类模糊说法掩盖
- 构建通过 ≠ 用户验证通过，要区分清楚
- 引入的 bug 要主动说明（例：曾误写 `UI.Divider = nil` 会破坏全局，发现后立即修正）

- `scripts/`：游戏代码（入口 `main.lua`）

  - `systems/`：经济/军事/外交/AI/战争/科技系统

## 技术要点（易错处）

- **长度单位是米**；Y-up 左手坐标系（同 Unity）
- **Lua 数组索引从 1 开始**
- **UI 用 `urhox-libs/UI`**（原生 UI 已废弃）；按钮用 `Show()/Hide()` 控制显隐，
  **不要改 `props.display`**（无效）
- **NanoVG 渲染必须用 `NanoVGRender` 事件**；字体只在 `Start()` 创建一次
- **鼠标按钮用枚举** `MOUSEB_LEFT`，不要用数字 0
- **UI 库没有 `InvalidateLayout`**，表构造器里不能写 `refs.x = 值`（非法 Lua）
- 引擎对象释放用 `Dispose()`
